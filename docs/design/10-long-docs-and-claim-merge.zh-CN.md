# 10 — 长文档分段抽取与重复断言合并

> 状态：**已实现**（2026‑10‑03；§9 的五项按建议定）。改的是 [09 — 处理流程重排](09-ingest-stage-rework.zh-CN.md) 里的两处：
> 「抽取」阶段（每篇一次调用、只读前 12,000 字），以及「判断」阶段的复核范围（从重复实体扩到重复断言）。
> 英文版：[10-long-docs-and-claim-merge.md](10-long-docs-and-claim-merge.md)。

## 0. 现状

数据取自 finance 工作区（2026‑10‑01，本机 PG 只读查询与文档 sidecar）：

| 项 | 数字 |
| --- | --- |
| `raw/docs` 文档 | 21 篇，**全部**超过 12,000 字；最短 2.0 万字，最长 36.8 万字，合计 513 万字 |
| 进了抽取的部分 | 每篇前 12,000 字，合计 25.2 万字，约 **4.9%** |
| 每篇抽取结果 | 21 篇全部顶满上限：实体 15、关系 15–20、断言 10 |
| 断言（claim） | 210 条（= 21 × 10），落在 141 个主体、**68 种** type 上；有第二份证据的 **0** 条 |
| 单次抽取耗时 | 中位数约 45 秒（多数在 27–63 秒；2026‑09‑15 那一轮，cursor-cli grok fast，并行 1。现在抽取跑在 codex 上，耗时会不同） |

这些文档是知识星球的月度归档：整月的每篇有 240–580 个二级标题（一帖或一段评论一个），每帖自带发帖时间；
正文常把 `#` 当项目符号，所以一级标题不可靠。

由此有三个问题：

1. **覆盖**。95% 的内容没进图谱，每篇的断言都来自月初一两天。原因只有一个：`LLM_EXTRACT_INPUT_CHARS`（`src/constants.ts`）。
2. **改动成本**。抽取结果按整篇内容哈希缓存，文档一改就整篇重抽。现在只读前 12,000 字，这个成本被截断藏住了；
   一旦读全文，每次改动都按全文付费，像当月归档这种持续追加的文档，每追加一次就整篇重付一次。
3. **重复断言**。断言 id = 哈希(主体 + 规范化原文)（`claimId`，`src/graph/store.ts`），措辞不同就是两条。
   同一个事实（"中际旭创 2025 年归母净利润 98–118 亿元"）会在多个帖子、多家券商、多个月份里被转述，读全文后这类重复会成倍出现。
   现有的两道检查都接不住：
   - 夜间 claim 审计（`auditClaims`，`src/wiki/refine.ts`）只在「同主体 + 同 type」组内比词重叠 ≥ 60%。type 由模型随手填
     （210 条用了 68 种，earnings 与 financials 混用），多数重复根本不在一个组里；就算查到，也只出一条「待核对」建议，不合并。
   - 来源冲突检测（`detectDisputes`，`src/lineage/trust.ts`）把「同主体同 type、时间重叠、原文不同」都当成矛盾——隔离来源对可信断言的**转述**也会开出争议。

## 1. 决策

| 决策 | 结论 |
| --- | --- |
| D1 分段 | 超过 `extraction.segmentChars`（默认 12,000）的文档按段抽取，每段一次调用；不超过的仍是一次调用。切点落在标题、分隔线、空行处，由切点处的内容决定，而不是由累计长度决定 |
| D2 段缓存 | 每段的结果按段文本哈希存进 sidecar：文档改动只重抽变了的段，中途停下也不丢已付费的段 |
| D3 文档主体 | 第一段先跑，并顺带回答「这篇文档主要讲谁」（可为空）；其余段带着它并行。「公司 / 本公司 / the company」这类泛指不建实体 |
| D4 只写入一次 | 全部段完成后先做文档内归并（同名实体合一、完全相同的断言去重），再作为一个 tier1 scope 写入；sidecar 仍存文档级结果，重建零调用 |
| D5 按调用排队 | `batchSize` 改为「每轮最多调用次数」（抽取按段计、摘要按篇计），长文档跨轮续跑；有积压时一轮接一轮，不等间隔。不设段数或 token 上限 |
| D6 断言合并是链接 | 与实体合并同一套机制：`claims.canonical_id` + `claim_links`，由 `claim-merge` scope 持有，`unmerge` 可拆，证据不改写 |
| D7 一次判断分五类 | 候选对交给「判断」模型，分 same / contains / conflict / different_time / unrelated。same 与 contains 合并；conflict 出知识建议，取代夜间 60% 词重叠检查；判过的对记住，不再重判 |
| D8 自动合并 | 新增 `review.claimMerge`（off / suggest / auto），**默认 auto**：只自动合并「规范化后逐字相同」，以及「判断为 same、置信 ≥ 0.9、数字与时间检查都通过」的对 |
| D9 存量回填 | 旧的截断抽取视为不完整，自动重新入队；装上后 finance 要补约 570 次调用 |

D5、D8、D9 与实体合并模式、实施顺序于 2026‑10‑03 确认，见 §9。

## 2. 调整后的流程

```
后台文档轮次 runDocumentPass（每轮：抽取最多 batchSize 次调用，摘要最多 batchSize 篇）
   ③ 抽取：按文档优先级挑出待抽的段 ── 段缓存命中的不调用
        每篇：第一段（顺带答出文档主体）─▶ 其余段并行（concurrency）
        全部段完成的文档：文档内归并 ─▶ 写入一个 tier1 scope ─▶ 记下本轮写到的实体与断言
      └▶ 增量消歧（实体，09 §3，不变）
      └▶ 增量断言合并（新）：只看本轮写到的断言 ─▶ 同主体候选 ─▶ 确定性检查 ─▶ 判断模型（成批）
            ─▶ 合并（可撤销）/ 建议 / 矛盾建议 / 记住结论
   ④ 摘要（不变）
   队列仍有积压 ─▶ 立即开下一轮；空了才按 intervalMinutes 轮询

夜间：全量实体消歧 → 全量断言合并兜底（含代表重挂）→ claim 审计（去掉词重叠一条）→ 断言复核 → 其余不变
```

## 3. 分段抽取

### 3.1 怎么切

输入和今天一样，是 `loadSourceText` 给出的 Markdown。

- **不超过 `segmentChars` 的文档就是一段**，读的文本与缓存方式和今天一样；新的上限和两条新规则（§3.2）对所有文档生效。
- 超过的，先按行切成「块」：标题行（任意级别）、`---` 分隔线、空行都是块的边界。`#` 被当成项目符号也无妨，只是多出几个候选切点。
- 从头往后装块。当前段超过 `segmentChars` 的四成后，若下一块是标题或分隔线、且其首行的哈希命中（约 1/12 的概率），就在这里切；
  装到 `segmentChars` 时在最近的块边界强制切。单块超长时先按段落、再按句子切。
- 段之间**不重叠**。每段带上它所在的标题路径（最近的一、二级标题）。

**为什么由内容决定切点。** 若按累计长度装满就切，文档开头改一个字，后面所有切点都会挪，几十段全部重抽。
由切点处的内容决定时，切点只和附近的内容有关：中间插一段，只有它所在的段（偶尔连带下一段）会变；末尾追加只影响最后一段。

**参数是实测定的**（finance，513 万字，上限 12,000，每篇随机插入 6 次）：

| 规则 | 段数 | 平均段长 | 一次插入后要重抽的段（平均 / 最多） |
| --- | --- | --- | --- |
| 四成以后、1/12 命中（采用） | 571 | 9,000 | 1.6 / 6 |
| 七成以后、1/2 命中（最初的设想） | 560 | 9,200 | 2.8 / 21 |
| 按长度装满再切 | 444 | 11,600 | 5.2 / 21 |

最短长度不能设得太高：段若总在「七成」之后不远处结束，切点又由长度决定，一处插入会让后面二十多段跟着变。
代价是段比装满时多约三成（每段平均 9,000 字），换来改动只重抽一两段；每段更短，单段的抽取上限也更不容易顶满。

### 3.2 每段一次调用

系统提示沿用今天的抽取提示（本体词表、claim 规则），用户消息开头加一个段落头：

```
Document: <标题> (<路径>) · part 3 of 26 · section: <标题路径>
Document date: 2025-08-01
Main subject of this document: 宁德时代 (organization)   ← 只在第一段答出了主体时才有
Known entities: …                                       ← 见下
```

- **第一段**额外回答 `subject`：这篇文档主要讲的那个实体；讲很多对象（归档、周报）时为 null，其余段也就不加这一行。
  其余段等第一段完成后并行跑。
- **已知实体**：`knownEntitiesIn` 改按**本段**文本取（最多 30 个），再加上同一文档已抽完的段里、在本段文本中出现过的实体，让同一篇里的叫法保持一致。
- 新增两条规则，单段文档同样适用：
  - 「公司 / 本公司 / 该公司 / the company」这类泛指不建实体：能从上下文确定指谁，就记在那个实体名下；确定不了就不抽。
  - 相对日期优先按段内自己写明的时间换算（帖子的发帖时间、带日期的标题），没有才用文档日期。归档里每帖都有时间，而文档日期只到月份。
- **每段上限**：实体 25、关系 30、断言 25（今天是每篇 15 / 20 / 10，21 篇全部顶满），`maxTokens` 从 8,000 提到 12,000。
  上限防的是输出过长被截断——截断的 JSON 解析失败，整次调用作废——不是预算。实测里归档这类密集内容一段就能顶满 25 条（§8）。

### 3.3 文档内归并

全部段完成后、写入之前，把各段结果合成一份文档级结果。规则都是确定性的：

- **实体**：名称 key、别名 key（`entityKeys`，`src/graph/normalize.ts`）或 `sameAs` 相同、且类型兼容的归为一个。
  名称取出现次数最多的写法（次数相同取先出现的），别名取并集，描述取第一个非空的，类型按多数。
- **关系**：端点映射到归并后的实体，按（源，谓词，目标）去重；以先出现的为准，缺的描述和有效期由后面的补上。
- **断言**：主体映射到归并后的实体，再按（主体，规范化原文）去重；每条记住来自哪一段。
- **落点**：断言落在**本段**内重合度最高的切块上（今天是在全文里找）；实体提及在每个抽到它的段里各取至多 4 个切块
  （今天是全文前 8 个命中），长文档的提及因此分布在全文，而不是挤在开头。

### 3.4 缓存、续跑与失败

文档 sidecar 的 `tier1.json` 加两个字段，原有字段不变：

```jsonc
{
  "status": "done",                    // 新增 'partial'：还有段没抽完
  "entities": [], "relations": [], "claims": [],   // 文档级归并结果，sync 重放照旧读这里
  "model": "…", "contentSha": "…", "extractedAt": "…",
  "segmenter": 1,                      // 新增：切段规则的版本
  "segments": [                        // 新增：每段一条（一次读完的文档也有一条）
    { "i": 0, "sha": "…", "start": 0, "end": 11234, "heading": "…", "status": "done",
      "subject": "宁德时代", "entities": [], "relations": [], "claims": [], "model": "…", "extractedAt": "…" }
  ]
}
```

- 每段一完成就写进 sidecar。App 退出或这一轮停下，下次接着跑，已付费的段不会重来。
- 文档改了：重新切段，`sha` 在旧 `segments` 里出现过的段直接复用（与位置无关），其余重抽，然后归并、写入。
  写入仍是替换整个 tier1 scope，被删掉的段所贡献的证据随之撤下。
- 一段连续失败 3 次：跳过这一段，用其余段的结果写入，sidecar 记下失败的段与错误。文档内容再变时会重试；
  `knode-os extract --retry-failed` 也可以手动重排。
- **重放规则**（`replayableTier1`）：`status` 为 done、`contentSha` 一致，并且 `segmenter` 是当前版本、或文档不超过旧版一次调用读的 12,000 字（`LEGACY_EXTRACT_CHARS`），才可重放。
  旧 sidecar 没有 `segmenter`，长文档因此重新入队——这就是 D9 的回填。新结果写入之前旧证据一直有效，图谱不会出现空窗。

### 3.5 排队与一轮的大小

- `extraction_queue` 仍按文档排、按文档算优先级，新增 `segments_total`、`segments_done` 两列给界面显示进度。
- 一轮按文档优先级依次取待抽的段，凑满 `batchSize` 次调用为止。第一段未完成的文档先排第一段，并为它的其余段预留本轮剩下的调用：
  第一段一完成，其余段就在同一轮里并行跑，一篇文档抽完再轮到下一篇。`concurrency` 是这些调用的并行数，跨文档共用。
- 一轮因此有界（8 次调用，按实测每次约 2 分钟、并行 1，约 16 分钟）：新进来的热门文档不必等一篇 36 万字的归档整篇抽完；
  初始化补抽的时限（`research.init.extractionMaxMs`，在轮与轮之间检查）也重新准确。
- serve 的定时器：一轮结束时队列仍有积压且这一轮有进展，就立即开下一轮；队列空了（或一轮毫无进展）才回到每 `intervalMinutes`
  分钟轮询一次。否则每轮结束后都要空等到下一次定时器跳动。
- 摘要仍是每轮最多 `batchSize` 篇。

## 4. 重复断言合并

### 4.1 什么算同一条

只在同一主体（合并后的规范实体）的断言之间比较。两条断言的关系分五类：

| 关系 | 含义 | 处理 |
| --- | --- | --- |
| same | 同一事实、同一时期、数字一致，只是措辞不同 | 合并，表述更清楚完整的那条做代表 |
| contains | 一条说了另一条的全部，还多说了些（A 说了营收和净利润，B 只说净利润，数字相同） | 合并（链接记为 `contains`），信息更全的那条做代表 |
| conflict | 同一事实、同一时期，数字或结论对不上 | 不合并，出一条「矛盾的断言」知识建议 |
| different_time | 同一指标、不同时期（25Q2 与 25Q3；2024 年实际与 2025 年预告） | 不合并，交给已有的新旧替代（`markSupersededClaims`） |
| unrelated | 其余，包括各有对方没有的事实的部分重叠 | 不处理 |

`absent`（查无结果）类断言不参与合并。

### 4.2 找候选

范围：每轮是本轮写到的断言（`applyExtraction` 增加返回 `claimIds`），夜间是全部代表断言。每条只和**同一规范主体**下的代表断言比较
（主体经实体合并展开），另外比一组「主宾互换」的（A 的主体是 B 的宾语、A 的宾语是 B 的主体）。三种信号：

1. **规范化后逐字相同**：在 `claimId` 已做的规范化之上，再去掉标点、统一全半角与数字写法。这类直接算 same，置信 1，不调模型。
   今天「…同比增长 20%。」与「…同比增长20%」是两条。
2. **向量相似度** ≥ 0.85（待校准）：文本取「主体：原文」，在同主体内取最近的 5 条。
3. **关键数字重合**：两条里带单位的数字（亿、万、%、pct、倍、元、美元……）有交集且时期相同。财务事实被转述时，数字往往比措辞更稳，
   所以有相同数字的一对，余弦门槛从 0.85 降到 **0.70**（`numberThreshold`，与 0.85 一样按 bge-m3 校准）。数字只降低门槛、不代替门槛；
   这一对自己的余弦也算数，不必落在最近的 5 条里。数字按两者中较粗的精度比：36.19 亿与 36.2 亿、0.45% 与 0.5%、14.9% 与 15% 算同一个数。

   最初的做法是向量分数不够、只要有相同数字也进候选。对 finance 已判的 28,974 对做的只读回测（2026-10-19）显示了代价：
   其中 15,831 对（55%）只靠数字相同找出，促成合并、建议或矛盾标记的结论只有 140 个（0.9%），而且几乎都离相似度门槛不远：

   | 只靠数字相同找出的对 | 对数 | 促成合并、建议或矛盾标记的结论 |
   | --- | --- | --- |
   | 余弦低于 0.70 | 8,527 | 3（0.04%） |
   | 0.70–0.75 | 3,281 | 22（0.7%） |
   | 0.75–0.80 | 2,378 | 35（1.5%） |
   | 0.80–0.85 | 1,645 | 80（4.9%） |
   | *对照：相似度 0.85–0.90* | 9,088 | 483（5.3%） |

   0.70 的门槛省掉全部判断的 29%，1,628 个有结果的结论只少 3 个。改成必须有相似度信号（这些对一律不要）会丢掉全部 140 个，
   其中有 208 个矛盾里的 46 个。要求更多相同数字也分不开：按审计的计法，相同 1 个、2 个、3 个及以上时分别是 0.9%、1.1%、0.7%。

用本地哈希 embedder（向量没有意义）时跳过第 2 条，改用今天的词重叠 ≥ 0.6，只有相同数字也仍进候选。用真实向量时，
嵌入失败的断言（比如嵌入池当天的额度用完）先不按数字找候选，等之后某一轮嵌入了再比，不会只凭数字交给模型判。
2026-10-19 的 finance 上，有同主体断言可比的 19.1 万条里有 15.9 万条还没有向量（夜间嵌入在嵌入池额度用完时停下），
等着判断的 182,476 对数字相同的对里有 181,460 对属于这种情况。

向量存在新表 `claim_embeddings`（`claim_id`、`model`、`embedding halfvec(维度)`），与 `entity_embeddings` 一样随向量维度建表、换维度时删除。
断言原文是 id 的一部分、不会变，所以每条只嵌入一次；换了 embedding 模型时按 `model` 列懒重算。
同一主体下的断言不多，按 `subject_id` 过滤后精确比较即可，用不着 HNSW——HNSW 也下推不了这种等值过滤。

### 4.3 判断前的确定性检查

| 检查 | 结论 |
| --- | --- |
| 两条都有事件时间或有效期，且按声明的精度不重叠 | different_time，不调模型 |
| 原文里的时期标记（年、季度、月；「2025 年四季度」与「25Q4」统一后再比）两边都有且不同 | different_time，不调模型；统一不了的当作兼容 |
| 两边都有关键数字，同一时期而数字不一致（舍入差异不算） | 交给模型，**不会**被自动合并 |
| 否定不一致（未、没有、尚未、否认、不会、不是……一边有一边没有；单个「不」不算，「不及预期」不是否定） | 交给模型，不会被自动合并 |
| 状态一边 fact、一边 disputed | 交给模型，不会被自动合并 |
| 这一对已有结论 | 跳过 |

结论记在新表 `claim_pair_verdicts`（`pair_id` = 哈希(排序后的两个 id)、关系、置信、理由、模型、时间）。
不记进 `suggestions`：断言比实体多一个数量级，`suggestions` 只放需要人看的东西。

### 4.4 判断模型

- 走「判断」路由（`ctx.llm`），**成批**：一次调用判至多 12 对，不分主体。实体消歧今天是一对一次调用；断言量大，一对一次会让判断调用比抽取还多。
- **每轮至多判 `review.claimMergeMaxJudgedPerRun` 对**（默认 1,200，即 100 次调用），最有希望的先判：相似度信号找出的对排在只靠数字相同找出的对前面；
  §4.3 里没有一条拦着不让自动合并的对排在其余的前面；再按相似度高（只靠数字相同找出的对按余弦高）、相同的关键数字多、断言新排。
  其余的对没有结论，下一轮还会被提出，夜间那轮比较全部断言。
  逐字相同、时期不同的对由 §4.3 定，不调模型，也从不排队。不设上限时，积压会拖住 tier 2 的其余步骤：finance 最大的两次夜间运行判了 7,531 和 9,252 对，
  各用了约四小时（每次调用约 20 秒）。按这个顺序，finance 已判的 28,974 对（2026-10-19）里，促成合并、建议或矛盾标记的 1,628 个结论有 681 个落在前 1,200 对；
  按当时判的顺序是 141 个。只靠数字相同找出的对占已判的 55%，其中有结果的只有 0.9%。§4.2 的余弦门槛现在去掉其中的 54%；
  剩下的按余弦排，它们 137 个有结果的结论有 41 个落在这类对的前 500 对里，按相同数字多少和新旧排时是 14 个。
- 每对给出：主体；两条的原文、type、状态、事件时间 / 有效期 / 文档日期、来源路径；各自落点切块的 300 字摘录。
- 规则：只有一条蕴含另一条（同样的事实、同一时期、同样的数字）才算 same；舍入后一致的数字算同一个数，超出舍入的不同才是 conflict；
  时期不同是 different_time；拿不准就给低置信。每对返回 `{relation, keep: "a" | "b", confidence, reason}`，理由用断言的语言写。
  「舍入后一致」这一条是实测后加的：海康威视同一季报的两种转述（0.45% / 0.5%、36.19 亿 / 36.2 亿、15% / 14.9%），
  模型按「数字不同就不是同一事实」判成了矛盾（§8）。

### 4.5 按模式处理（`review.claimMerge`）

| 结论 | auto | suggest | off |
| --- | --- | --- | --- |
| 规范化后逐字相同 | 合并 | 合并 | 不处理 |
| same / contains，置信 ≥ `claimMergeMinConfidence`（0.9），且 §4.3 的检查都通过 | 合并 | 建议 | 不处理 |
| same / contains，置信 ≥ `llmMinConfidence`（0.6）但够不上上一行 | 建议 | 建议 | 不处理 |
| conflict，置信 ≥ 0.6 | 「矛盾的断言」知识建议 | 同左 | 不处理 |
| different_time、unrelated、低置信 | 记住结论 | 记住结论 | 不处理 |

逐字相同在 suggest 下也直接合并：这和今天 `claimId` 的去重是同一类事，只是规范化多走了一步。
合并建议的 `kind` 是 `claim-merge`：接受即合并，拒绝即记为 unrelated。

### 4.6 合并怎么表示

完全照实体合并（`src/graph/merge.ts`）来：

- 新列 `claims.canonical_id`，新表 `claim_links`（`id`、`claim_id`、`canonical_id`、`kind`（`same_as` / `contains`）、
  `scope_id`、`actor`、`reason`、`confidence`、`created_at`、`tx_to`）。
- 每次合并是一个 `claim-merge` scope（key = 被合并的断言 id），通过 writer 新增的效果 `linkClaim` 写入，逆操作是 `claim_link.remove`；
  `knode-os claim unmerge <id>` 处理掉这个 scope 即复原。账本写 `claim.merge` / `claim.unmerge` 反馈，`rebuild` 能重放。
- **代表**：已经有组员的一方保持代表不变（代表的 id 被引用时保持稳定）；否则取判断给出的 `keep`（信息更全的那条），没有就取证据多的，
  再取先出现的。组是扁平的：合进一个已被合并的断言，会落到它的代表上；代表并入别的组时，它的组员一起挪过去，拆开时再挪回来。
- **折叠**：代表行按「自己的证据 ∪ 组员的证据」折叠（复用 `foldClaimEvidence`），于是 `evidence_count` 就是来源数，
  状态、有效期、首个来源都像今天完全相同的断言那样合起来；组员的证据有变化时代表一起重折。组员行保留各自的折叠，拆开时立即复原。
- **读取**：所有读「当前断言」的地方加 `canonical_id IS NULL`——`v_claims` 视图、`knode_claims`（`src/store/claims.ts`）、
  knode_ask 的已知事实（`src/search/ask.ts`）、图谱查询、实体页与时间线、推荐与 survey、lint、compiler 的 absence 与 subscribe，约 30 处 SQL。
  断言记录增加 `sources`（组内全部来源路径），回答里可以写「3 个来源」。
- **代表失去自己的来源**（它的文档被删了）而组员还在：折叠靠组员的证据保持存活；夜间兜底把组员中证据最多的那条提为代表，重挂链接。
- **与其他机制的关系**：
  - 实体合并：候选按规范主体取。挂在两个重复实体下的重复断言，要等这两个实体合并之后才会被比到。
  - 新旧替代：只在代表之间算。
  - `detectDisputes`：同组的两条不再算矛盾，转述不会再开争议。
  - 夜间 claim 审计：`claimMerge` 不是 off 时去掉「多来源相似断言」一条（由 §4.4 的 conflict 取代；off 时保留，作为唯一的近似重复提示）；过期、fact 与 disputed 冲突两条保留，只看代表。
  - 断言复核（`reviewClaims`）不变。

### 4.7 什么时候跑

- **每轮**：在增量实体消歧之后（`auto` 下的实体合并先生效）跑 `auditDuplicateClaims(ctx, { focus: 本轮写到的断言 })`，然后才写摘要。
- **夜间**：`refineWiki` 的顺序改为 全量实体消歧 → 全量断言合并（兜底两条都是旧断言、主体刚被合并、换过 embedding 模型的情况，并重挂代表）
  → claim 审计 → 断言复核 → 其余不变。

## 5. 配置、接口与迁移

```jsonc
"extraction": {
  "segmentChars": 12000,   // 新增：一段的上限（字符）；不超过的文档仍是一次调用
  "batchSize": 8,          // 含义改为每轮最多调用次数：抽取按段计、摘要按篇计
  "concurrency": 1, "intervalMinutes": 5, "claims": true
},
"review": {
  "claimMerge": "auto",             // 新增：off / suggest / auto
  "claimMergeMinConfidence": 0.9,   // 新增：auto 合并的置信门槛
  "claimMergeMaxJudgedPerRun": 1200 // 每轮判定的对数，最有希望的先判（§4.4）；其余留给之后的运行

```

  `v_claims` 视图追加 `canonical_id` 列并只出代表；`claim_embeddings` 写进 `embeddingsDdl`（`src/store/db.ts`）。
- **配置迁移**：不用改写文件。新键都有默认值，`batchSize` 的值照用。
- **`PUT /api/config`**：接收 `review.claimMerge`；`segmentChars`、`claimMergeMinConfidence`、`claimMergeMaxJudgedPerRun` 只能改配置文件。
- **CLI**：`knode-os extract` 输出调用数与剩余段数，`--retry-failed` 先把有失败段的文档重新入队；新增
  `knode-os claim merge <claim> <into>`、`claim unmerge <claim>`、`claim merges`、`claim dedupe`
  （`claims` 已经是查询命令，所以用单数）。
- **API**：`GET /api/claims/merges`、`POST /api/claims/merge`、`POST /api/claims/unmerge`（与实体合并的接口同形）；

## 7. 代价（按 finance 估算）

- **回填抽取**：finance 切成 **571 段，即 571 次调用**（今天是 21 次）。实测 codex（gpt-6.1-sol）每段 113–144 秒、平均约 2 分钟：
  并行 1 约 20 小时，并行 3 约 7 小时（「并行调用」在抽取阶段里改）。按估算每次约 8,000 tokens（含输出），合计约 460 万 tokens。
  这是一次性的，之后只为新增和改动的段付费。
- **断言数量**：从 210 条涨到一万条上下（合并前；实测每段 24–25 条，见 §8）。合并率在回填后实测。
- **embedding**：每条新断言一次请求。
- **判断调用**：12 对一次，每轮至多 `claimMergeMaxJudgedPerRun`（1,200）对，规模在回填后实测；时期不同、逐字相同这两类先被确定性检查挡掉，不调模型。
  只靠数字相同的对要余弦 0.70（§4.2），按 finance 截至 2026-10-19 的判断量能省 29%。
- **实体**：实体数也会从 261 涨到数千，`llmJudge = suggest` 下待确认的实体合并建议会同比增加，见 §9 第 4 条。

## 8. 验证

**单元测试**

- 切段：不超过 `segmentChars` 时只有一段，输入文本与今天相同、不加段落头；中间插入一段文字，最多 2 段的哈希改变；末尾追加只改变最后一段；`#` 项目符号不影响结果。
- 文档内归并：同名、同别名、`sameAs` 的实体合一；完全相同的断言去重；断言落点在本段之内。
- 缓存与续跑：抽到一半停下，下一轮不再调用已完成的段；改一段只重抽那一段；sync 重放仍然零调用；旧 sidecar 里的长文档重新入队，短文档不动。
- 合并：逐字相同直接合并；数字不同永远不会被自动合并；时期不同不调模型；合并后再拆开，两条断言与折叠计数都复原；读取只出代表；
  新旧替代与 `detectDisputes` 不看组员；`rebuild` 能重放合并。

**在 finance 上对比**：取 3 篇长文档，沿用 `bench extract-compare` 的裁判打分方式。

- 覆盖：至少有一条断言落点的段占多少；
- 准确：随机抽 50 条断言，让裁判对照落点切块判断有没有依据；
- 每篇的断言数、实体数、调用次数、耗时；
- 比较 `segmentChars` 8,000 与 12,000、新旧两组上限，再定默认值。

**合并质量**：先用 suggest 在 finance 上跑一遍，人工看 30 条合并、20 条矛盾，再切到 auto。

**实测（2026‑10‑03，临时工作区，finance 现在的抽取与判断配置）**：取 2025‑08 归档开头 2.65 万字。

- 切成 3 段，3 次 codex 调用：113、144、127 秒。第一段答出的文档主体是 null（归档讲很多公司，符合预期）。
- 写入 53 个实体、74 条断言；旧办法读前 12,000 字，每篇只有 15 个实体、10 条断言。
- 第 2、3 段的实体和断言都顶到了 25 条的上限：归档内容很密，每段的信息没有抽全。要更全，可以把 `segmentChars`
  调小（8,000 约 800 次调用）或提高上限（输出更长、每次更慢），先按现在的设置回填，再看效果。
- 断言合并：2 对候选，判断 2 对。其中海康威视同一季报的两种转述（数字只差舍入）被判成矛盾，据此加了舍入规则（§4.3、§4.4）。
  加上之后重判：这一对判为 contains（置信 0.98）并自动合并，代表是信息更全、多了「现金流大幅提升」的那条；
  它与另一条「2025 年全年及 2026–2027 年预测」判为 different_time。一次判断调用 46 秒，判了 3 对。

## 9. 已定的取舍

1. **断言合并默认 auto。**数量上，回填后的合并候选会有成百上千对，suggest 意味着每一对都要人点；
   风险上，断言合并只影响这一条断言的显示和计数（实体合并会牵动提及、关系和页面），而且随时可以拆开。
2. **装上后自动回填。**截断不是质量上的取舍，而是缺了 95% 的内容。代价是 finance 约 570 次调用；按实测每次约 2 分钟，并行 1 约 20 小时、并行 3 约 7 小时。
3. **`batchSize` 改成「每轮调用数」。** 不改的话，一轮要抽完 8 篇整月归档（约 170 次调用、两个多小时），
   新文档得等整轮结束，初始化补抽的时限也形同虚设。
4. **实体合并暂不改，仍是 suggest。** 实体合并会牵动提及、关系和页面，风险比断言合并大；回填后实体合并建议会大量出现，看实际的量再定 `llmJudge`（09 · D5）。在「判断」阶段随时可以切到 auto。
5. **两部分一起实现，断言合并与回填同时生效。** 否则回填期间会先积出一批重复断言、争议和「待核对」建议。

## 10. 已知限制

1. 经常变化的文字会让段哈希失效。比如归档帖子元信息里的阅读数、评论数，若重新渲染时这些数变了，所在的段就要重抽。
   应在语料侧（归档渲染脚本）处理，不在产品里做模糊复用：「看起来差不多就沿用旧结果」会把改过的数字留成旧值。
2. 跨段只传文档主体。一段里提到的对象若只在很远的另一段点过名，要靠写入后的实体消歧接住。
3. 断言只在同一规范主体（以及主宾互换）之内比较；挂在两个尚未合并的重复实体下的重复断言，要等实体合并后才会被发现。
4. 各有对方没有的事实的部分重叠不合并。
5. 摘要仍只读前 14,000 字（`LLM_WIKI_INPUT_CHARS`），长文档的摘要页同样只反映开头。这不在本文范围，后续可以用各段的抽取结果来写摘要。
6. 按系统时间回看（`as_of`）时，断言按**现在**的分组过滤，代表也只折叠它自己当时的证据：合并之前的时间点看到的是合并后的分组。
