    02 · PIPELINE

    What each stage needs

    A document moves down this list. The stages ask different things of a model, which is why each one can run somewhere else.

    Per stage

    Convert

    Vision

    Images and scanned PDF pages become searchable Markdown.

    The model has to see pixels: an API provider gets the image inline, codex takes --image, and claude and cursor read the file with their own tools. A text-only model fails here. Changing this re-converts every image and scanned page.

    Index

    Embedding

    Every chunk becomes a vector for semantic and hybrid recall.

    Not an LLM — it uses one of the embedding providers from section 01. Changing which one, or its model or dimensions, re-embeds the whole corpus.

    One provider at a time — vectors from two models are not comparable. Switching re-embeds the whole corpus when you save.

    Extract

    Volume

    Names entities, relations and factual claims in changed documents.

    The busiest stage — it runs on every changed document, bounded by the batch size here. A fast, cheap model that returns clean JSON is usually the right trade.

    Synthesize

    Quality

    Turns hot entity clusters into readable, linked Concept pages.

    Far fewer calls than Extract — only hot clusters reach it — and the output is prose people read, so a stronger model pays for itself here.

    Summarize

    Judgment

    Writes each document's summary page and answers knode_ask; overnight it runs Dream and reviews duplicate entities and disputed claims.

    Every job here reads the text it is handed and makes a call on it — what a document is about, whether two entities are one, which of two claims holds, what a week of agent sessions says. Nobody waits on most of them: summaries are written when the wiki is generated and refreshed overnight, beside Dream and the reviews, so a slower model or a CLI subscription only costs time. knode_ask is the exception — an agent is waiting on its answer.

    What initialization does, how Ask behaves, and how a deep-research job runs: which agent from section 01 takes it, how the phases fan out, and the verification bar the profile sets for its sub-agents.

    AskAsk uses the same agent research does: it answers over MCP, and writes what you teach it as a quarantined note. Effort, turns, timeout, tool grants and any extra prompt come from the agent — edit them where the agent is defined, in section 01.
    Ask
    Profile Stored as playbooks/research/profiles/<name>.yaml — edit here or in the file. The profile may pin its own pipeline.
    Sub-agentsOne card per role. Each has its own CLI, model, effort, tools and prompt; turn a role off to skip its phase. Several roles may share a phase (review roles all run; research roles split the sections).
